# Венское кафе: правила для Claude Code

Этот файл Claude Code читает автоматически при каждом запуске в репозитории. Здесь то, что нельзя нарушать.

## О проекте

Собственный сайт кафе «Венское» (Чита) вместо Tilda: меню, корзина, доставка и самовывоз, онлайн-оплата через интернет-эквайринг Сбербанка, отслеживание заказа гостем, Telegram-бот для сотрудников, админка. Сайт работает на живой бизнес: ошибка в заказах или деньгах стоит реальных денег.

Владелец проекта знает Go на начальном уровне и учится на этом коде. Поэтому код должен быть простым и понятным, а не хитрым.

Перед любой задачей прочитай:
- `docs/architecture.md` — части системы, жизнь заказа, возвраты, бот, админка, правила оплаты;
- `docs/roadmap.md` — этапы и ветки;
- `docs/payments-sber.md` — конспект API Сбера; оригинал спецификации в `docs/sber-ecom-api.yaml`, сверяйся с ним по каждому методу;
- `docs/workflow.md` — git и пул-реквесты.

## Стек и версии

- Go: версия из строки `go` в `backend/go.mod`. **Не повышай её.** Команды Go запускай с `GOTOOLCHAIN=local`, чтобы не скачивался новый тулчейн.
- Новые зависимости: только если без них заметно хуже. Выбирай версию, совместимую с нашей версией Go; после `go get` и `go mod tidy` проверь, что строка `go` в `go.mod` не изменилась. Если изменилась, бери версию старше.
- Уже закреплено: `jackc/pgx/v5 v5.7.6`, `pressly/goose/v3 v3.26.0`, `caarlos0/env/v11`. Не обновляй их без отдельной задачи.
- HTTP: стандартный `net/http.ServeMux` с шаблонами Go 1.22 (`"GET /api/menu"`), без фреймворков.
- Логи: `log/slog`. База: PostgreSQL 17, пул `pgxpool`, SQL пишем руками, строки в структуры через `pgx.RowToStructByName`.
- Миграции: goose, один файл `NNNNN_name.sql` с секциями Up и Down, встраиваются через `migrations/embed.go` и применяются при старте. Новая миграция создаётся через `make migrate-new name=...`. **Слитые в main миграции никогда не редактируем**, только добавляем новые.

## Как устроен код

```
backend/
  cmd/api/main.go        только сборка зависимостей и запуск, без логики
  internal/config        настройки из env (caarlos0/env), проверка значений
  internal/db            подключение и миграции
  internal/httpapi       HTTP: маршруты, обработчики, middleware, writeJSON/writeError
  internal/<домен>       бизнес-логика по темам: menu, delivery, orders, payments, sber, telegram, admin...
  migrations             SQL-миграции
  seed/dev.sql           тестовые данные только для локальной разработки
```

- Пакеты предметной области ничего не знают про HTTP. Обработчики в `httpapi` разбирают запрос, вызывают домен и пишут ответ.
- Зависимости обработчиков передаются через структуру `httpapi.Deps` и интерфейсы, чтобы в тестах подставлять заглушки.
- Каждый внешний сервис (Сбер, DaData, Telegram) спрятан за интерфейсом в своём пакете. В тестах вместо него заглушка или `httptest.Server`. **Тесты никогда не ходят в настоящую сеть.**
- Ошибки API всегда в одном формате: `{"error": {"code": "...", "message": "..."}}`. `code` для программы (латиница, snake_case), `message` по-русски для человека. Текст внутренней ошибки идёт только в лог, не в ответ.
- У каждого обработчика, который ходит в базу или наружу, свой `context.WithTimeout`.
- Фоновые задачи (сверка оплат, автоотмена, бот, рассылка) запускаются из `main.go`, получают общий `ctx` и корректно останавливаются при SIGTERM вместе с сервером.

## Правила предметной области

- **Деньги** только целыми числами в копейках (`int64`, колонки `bigint`, суффикс `_kop`). Никаких `float`.
- **Сумму заказа считает только сервер** по ценам из базы. Цены и суммы из запроса браузера игнорируются.
- **Время** в базе в `timestamptz`. Часы работы, «сегодня», статистика и сводки считаются в часовом поясе `Asia/Chita`. В `main.go` должен быть импорт `_ "time/tzdata"`, потому что в distroless-образе нет базы часовых поясов.
- **Статусы заказа** меняются только через одну функцию с таблицей разрешённых переходов (см. `docs/architecture.md`). Каждая смена пишется в `order_events` (кто: guest/staff/bot/system, из какого статуса в какой, когда, причина) в той же транзакции, что и смена статуса.
- **Сбер**: callback не подписан, ему не верим, всегда перепроверяем `getOrderStatusExtended.do`; оплачен только `orderStatus = 2`. Необязательные поля с `omitempty`, `null` не отправляем. Возврат сначала записывается в базу как `pending`, его ID уходит в `externalRefundId`. Всё остальное в `docs/payments-sber.md`.
- **Бизнес-значения** (минимальная сумма заказа, часы работы, зоны и цены доставки, данные кассы, ФФД, СНО, ИНН) не выдумывай. Храни их в базе или настройках, в seed ставь явные заглушки, а в описании PR перечисли в разделе «Нужно от владельца».

## Безопасность

- Секреты (пароли Сбера, токены DaData и Telegram, пароль базы) только в `.env`, который в `.gitignore`. Для каждой новой настройки добавь строку-заглушку в `backend/.env.example` и в `config.go`.
- Никогда не пиши в лог пароли, токены, данные карт, полный текст запросов к Сберу с `userName`/`password`. Телефон гостя в логах маскируй.
- Не обращайся к боевому контуру Сбера (`epay.sberbank.ru`) и к боевой базе. Ручная проверка оплаты только на `ecomtest.sberbank.ru` и только если владелец сам положил тестовые логин и пароль в `.env`.
- Интеграционные тесты очищают таблицы, поэтому хелпер тестов должен отказываться запускаться, если `DATABASE_URL` указывает не на `localhost`/`127.0.0.1`.
- Seed-данные никогда не попадают в боевую базу: seed не вызывается из кода приложения.
- SQL только с параметрами (`$1`), никогда не склеивай строки с данными пользователя.
- Никаких необратимых действий за пределами репозитория: не трогай сервер, DNS, настройки Сбера и Telegram.

## Тесты и проверки

- Перед каждым коммитом из папки `backend`: `make lint` и `make test` (поднять базу: `make db-up`). Перед пушем ещё `make build`. Всё должно быть зелёным.
- Чистую логику (расчёт суммы, переходы статусов, выбор reverse/refund, точка в полигоне) покрывай табличными тестами. Работу с базой — интеграционными тестами, которые пропускаются без `DATABASE_URL`. HTTP — через `httptest`.
- Тесты запускаются с `-race` и `-p 1` (так настроено в `make test`). Не отключай, не пропускай и не удаляй падающие тесты, чтобы стало зелёным: чини причину.

## Git

- Одна возможность — одна ветка от свежего `main`: `git switch main && git pull && git switch -c feature/<имя>`. Имена веток из `docs/roadmap.md`.
- Коммиты маленькие и по смыслу, Conventional Commits, текст по-русски: `feat(orders): создание заказа`, `fix(...)`, `test(...)`, `docs: ...`, `chore: ...`.
- Закончив ветку: `git push -u origin <ветка>` и пул-реквест через `gh pr create` с описанием по-русски: «Было:», «Стало:», «Как проверить руками» (команды `curl`), «Что стоит понять» (2–5 пунктов для владельца), «Нужно от владельца» (если есть).
- **Не сливай PR, не пушь в main, не делай force push, не переписывай историю main.** Сливает владелец после ревью и зелёного CI.
- Обнови `docs/roadmap.md` (галочка) и `README.md`, если появились новые команды или настройки. Если реализация разошлась с `docs/architecture.md`, поправь документ в той же ветке и объясни в PR почему.

## Как отчитываться

В конце каждой задачи напиши владельцу по-русски, простыми словами:
1. Что сделано и какие файлы главные (3–7 пунктов).
2. Как проверить руками, по шагам с командами.
3. Что в этом коде важно понять и почему сделано именно так.
4. Что осталось открытым или нужно от владельца.

Если задача упирается в неизвестное (бизнес-правило, данные банка, спорное архитектурное решение), не угадывай: остановись и спроси, предложив вариант по умолчанию.
