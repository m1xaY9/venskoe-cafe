# Интернет-эквайринг Сбербанка: конспект API

Источник — OpenAPI-спецификация платёжного шлюза Сбербанка версии 1.1.11 (файл [`docs/sber-ecom-api.yaml`](sber-ecom-api.yaml), присланный 22.10.2026). Здесь только то, что нужно сайту кафе. Перед реализацией каждого метода сверяемся с оригиналом: детали могут измениться.

## Подключение

| | |
|---|---|
| Тестовый контур | `https://ecomtest.sberbank.ru/ecomm/gw/partner/api/v1/...` |
| Боевой контур | `https://epay.sberbank.ru/ecomm/gw/partner/api/v1/...` |
| Формат | `POST`, `Content-Type: application/json`, UTF-8, TLS 1.2/1.3 |
| Авторизация | `userName` и `password` в теле каждого запроса (выдаёт банк после подключения) |
| Сертификат | шлюз использует сертификат НУЦ Минцифры: его корневой сертификат нужно добавить в доверенные у Go-клиента |
| Суммы | целые числа в **копейках** (199 ₽ → `19900`) |

Особенности:
- Параметры с пустым значением **не передаём вовсе**, `null` запрещён. В Go это `omitempty` на всех необязательных полях.
- Имена параметров чувствительны к регистру.
- У тестового контура бывают технические окна по будням: 02:00–06:00, 09:00–10:00 и 18:00–20:00 МСК, в Чите это 08:00–12:00, 15:00–16:00 и 00:00–02:00. Если тест вдруг падает, сначала проверяем время.
- Банк требует передавать email покупателя в заказе: на него приходит уведомление об операции.

## Методы, которые нам нужны

| Метод | Когда вызываем | Главное |
|---|---|---|
| `register.do` | гость нажал «Оплатить» | `orderNumber` — **номер попытки оплаты**, а не ID заказа: `"<order.number>-<attempt>"` (до 36 символов). Так гость может оплатить повторно после отказа банка, не упираясь в «номер уже обработан». Плюс `amount`, `returnUrl`, `failUrl`, `email`, `phone`, `sessionTimeoutSecs`, `orderBundle` (корзина для чека). В ответ приходят `orderId` (ID в Сбере, сохраняем) и `formUrl` (страница оплаты, туда редиректим гостя) |
| `getOrderStatusExtended.do` | callback, возврат гостя на сайт, фоновая сверка | по `orderId` или `orderNumber`. Смотрим `orderStatus` |
| `reverse.do` | отмена в тот же банковский день (до ~23:59 МСК) | `orderId`, `amount` (0 = вся сумма), `orderBundle` для чека возврата |
| `refund.do` | возврат после расчётов банков | `orderId`, `amount`, `jsonParams.externalRefundId` (ключ идемпотентности возврата), `orderBundle` |
| callback | Сбер сообщает об изменении | `mdOrder` (= `orderId`), `orderNumber`, `operation`, `status` |

## Статусы заказа в Сбере (`orderStatus`)

| Код | Значение | Что делаем |
|---|---|---|
| 0 | зарегистрирован, не оплачен | ждём |
| 1 | сумма захолдирована (двухстадийный) | у нас не используется |
| 2 | **оплачен** | заказ → `paid` |
| 3 | авторизация отменена (после `reverse`) | возврат завершён |
| 4 | был возврат (после `refund`) | возврат завершён |
| 5 | идёт 3-D Secure | ждём |
| 6 | авторизация отклонена | оплата не прошла, гость может попробовать снова |

## Callback

- Приходит POST на URL из настроек учётной записи (или `dynamicCallbackUrl` в заказе).
- `operation`: `deposited` (оплачен), `reversed`, `refunded`, `declinedByTimeout` (время на оплату вышло) и другие. `status`: 1 — успех, 0 — ошибка.
- **Подписи у callback в этой версии API нет.** Поэтому callback для нас только сигнал «проверь заказ», и сервер всегда перепроверяет статус через `getOrderStatusExtended.do`.
- Сбер делает только 3 попытки с интервалом 60 секунд, поэтому дополнительно работает фоновая сверка.
- Отвечаем `200` быстро, тяжёлую работу делаем после ответа.

## Идемпотентность

- `register.do`: заголовок `x-idempotencyKey` по документации **ещё в разработке**. Защищаемся уникальным `orderNumber`: повторная регистрация с тем же номером даёт ошибку 1 «Заказ с таким номером уже обработан». Тогда достаём существующий заказ через `getOrderStatusExtended.do` по `orderNumber`. `orderNumber` всегда уникален навсегда — поэтому это номер **попытки** оплаты (`"<order.number>-<attempt>"`): на каждую новую попытку гостя заводим новый `orderNumber`, а повторный `register.do` одной и той же попытки упирается в ошибку 1 и мы просто берём уже созданный платёж.
- `refund.do`: `jsonParams.externalRefundId` работает в рамках заказа и без ограничения по времени. Повтор с тем же ключом вернёт исходный ответ.

## Чеки 54-ФЗ

- Чек пробивает облачная касса (АТОЛ Онлайн, Эвотор, OFD.RU, Бизнес.Ру), подключённая к эквайрингу через СберБизнес.
- Чтобы чек сформировался, в `register.do`, `reverse.do` и `refund.do` передаём `orderBundle` с обязательными `ffdVersion` и `receiptType`. Доставку указываем в корзине отдельной позицией.
- Нужно уточнить у кафе: какая касса, версия ФФД (1.05 или 1.2), система налогообложения (`sno`), ИНН.
