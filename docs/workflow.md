# Как мы работаем: git, ветки, пул-реквесты, деплой

Здесь собраны правила, по которым меняется код. Они нужны, чтобы работающий сайт кафе не ломался от случайной правки.

## Главное правило

**`main` — это то, что сейчас работает у гостей.** В `main` никто не пушит напрямую. Любое изменение проходит путь: ветка → пул-реквест → зелёные проверки → слияние → автоматический деплой.

Защиту `main` включаем в настройках GitHub: Settings → Branches → Add rule для `main` → «Require a pull request before merging» и «Require status checks to pass».

## Ветки

Одна ветка на одну задачу. Ветка живёт, пока задача не влита в `main`, потом удаляется.

| Префикс | Для чего | Пример |
|---|---|---|
| `feature/` | новая возможность | `feature/cart`, `feature/telegram-bot` |
| `fix/` | исправление ошибки | `fix/min-order-check` |
| `chore/` | инфраструктура, зависимости, CI | `chore/ci-go` |
| `docs/` | только документация | `docs/deploy-guide` |

```bash
git switch main
git pull                          # всегда начинаем от свежего main
git switch -c feature/cart        # новая ветка
# ...работаем, коммитим...
git push -u origin feature/cart   # отправляем ветку на GitHub
```

Затем на GitHub открываем Pull Request из `feature/cart` в `main`.

## Коммиты

Пишем по [Conventional Commits](https://www.conventionalcommits.org/ru/): тип, двоеточие, коротко что сделано.

```
feat(cart): добавить изменение количества в корзине
fix(delivery): не пускать заказ ниже минимальной суммы
chore(ci): запускать go test на пул-реквестах
docs: описать процесс деплоя
```

Один коммит — одно логическое изменение. Так проще понять историю и откатить ровно то, что сломалось.

## Пул-реквест

В описании PR пишем:
- **Что было** и **что стало** с точки зрения гостя или сотрудника кафе.
- **Как проверить**: какие шаги пройти руками.

PR можно сливать, когда CI зелёный (сборка, линтер, тесты) и изменения проверены на тестовом окружении, если они касаются денег или заказов.

Сливаем через **Squash and merge**: в `main` попадает один аккуратный коммит на задачу.

## Окружения

| Окружение | Откуда | Для чего |
|---|---|---|
| локально | ваша машина | разработка |
| staging | ветка `main`, тестовый контур эквайринга Сбера | проверка перед боевым запуском |
| production | тег `v*` (например `v1.2.0`) | настоящие гости и деньги |

Пока сайт не запущен, будет одно окружение. Схему со staging и тегами включим перед запуском (см. roadmap).

## Секреты

Логин и пароль эквайринга Сбера, токен Telegram-бота и пароль от БД **никогда не попадают в git**. Локально они лежат в `.env` (он в `.gitignore`), на сервере хранятся в переменных окружения, а для деплоя в GitHub Actions — в Settings → Secrets.

Если секрет случайно попал в коммит, считаем его утёкшим: сразу перевыпускаем ключ. Удаления из истории недостаточно.
